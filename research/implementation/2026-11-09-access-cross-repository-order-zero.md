## Findings that determine the implementation order

1. **Key convergence is more than replacing a file loader.** `config/initializers/jwt.rb` invokes
   the local installer in local Rails environments, configures the registry and validates every
   private-key JWT registration after initialize. `lib/jit_security_jwt_local_keyset_installer.rb`
   generates missing EC signing material, persists it under `tmp/local_jwt_keysets.json`, exports
   several issuer/client families to ENV, and trims private variables for RP runtime roles.
   `app/values/oidc_client_assertion_jwt.rb` can call that installer again on a signing
   configuration failure. Removing only the initializer call leaves a second generation path.
   Neither path was executed or changed by this audit.
2. **Access currently has a local view of RP private keys.**
   `OidcClientRegistry::ClientConfiguration` has `jwt_namespace` but no `jwks_uri` field. Its
   private-key JWT boot validator asks the shared registry for each registered client's private key.
   `OidcClientAssertionJwt.verify` resolves the client namespace and obtains its verification key
   locally; it does not fetch that client's public JWKS. Remote verification and role-aware boot
   requirements must land before RP private material can be removed from Access.
3. **One repository key does not mean one authorization boundary.** The accepted amendment shares
   one signing set/JWKS per repository, including non-OIDC JWTs. Current registry checks require
   globally unique kids across issuer records and distinct Preference realm key material. Current
   JWKS controllers select an Auth/Visa namespace per host. Sharing a key/kid across those records
   would fail current validation; bypassing the validation would silently change a security
   contract. The implementation must explicitly reconcile these checks with the accepted repository
   scope and preserve strict token-type, issuer, audience, purpose, realm and transaction
   verification. Cross-repository key separation still remains.
4. **Local transport rewriting reaches beyond the token request.** Eleven production files directly
   call `OutboundHttp::LocalBackChannel`; the module itself is
   `app/lib/outbound_http/local_back_channel.rb`. They include JWKS, revocation, refresh, legacy RP
   token/UserInfo orchestration, sensitive admission and authority/capability clients. Removing the
   module without changing every caller/HTTPS flag leaves broken paths. The source appendix below
   lists every matched runtime/reference file, not just the first sign-in path.
5. **Transport controls exist but are not automatically universal.** `OutboundHttp::Connection`
   centralizes Faraday construction and follows no redirects. Public-address checking is an explicit
   builder option; many visible clients do not enable it. `OidcOpJwksClient` validates a fixed HTTPS
   URI and bounds document/key sizes with cached lookup, but still rewrites transport and its fetch
   does not request the public-address adapter. The new registered RP JWKS fetch needs the accepted
   frozen destination allowlist and checked, pinned public address, not an assumption that reusing
   this client supplies every SSRF control. The existing back-channel logout client already requests
   HTTPS/public-address checking and should retain its stronger policy.
6. **Retained RP code is not evidence of an Access RP surface.** Current `config/routes.rb` draws
   Auth, Visa and six guarded development tools. It does not draw Base/Core/Warp/Palm/Edit/Tech
   browser routes. Many named callers remain as concerns, operations, models or test infrastructure.
   Their retention matters to this change, but source presence does not establish reachability in
   Access or current behavior in another repository.

### Persistence and token contracts

- Client-assertion replay refusal is persisted through `SecurityConsumedJti.consume!` (currently
  `OpBaseAppRecord`), with purpose/issuer/JTI digest and a unique-insert refusal. Remote key lookup
  replaces key acquisition, not replay ownership, expiry enforcement or the atomic consume step.
  Moving this state to an evictable cache would weaken the current boundary.
- OP authorization, handoff, ceremony/session, grants and audit data remain Access-owned. The
  connection stage does not authorize deleting them or reassigning their databases. Governance must
  complete the local-cell RP path without reading Access databases, as the decomposition ADR
  requires. Visible RP record subclasses/configuration in this checkout are not proof that a
  separate RP repository already uses that isolation.
- Shared signing material cannot collapse `client_id`, App/Org realm, actor, tenant, audience,
  purpose, browser binding or transaction ownership. Ceremony contracts already verify header type,
  issuer, audience and purpose-specific payload; verify all families when replacing key selection.
  `OidcStateJwt` and client assertions are RP-signed; ID/access/logout tokens are OP-signed;
  external provider keys and DPoP proofs are different trust roots and must not be swept into
  repository signing-key consolidation.
- Existing opaque handles, sessions, encrypted data and audit history are preserved. The accepted
  future BFF browser model does not authorize changing current cookie contracts in this stage.
  Credentials/key rotation can invalidate outstanding tokens, signed state, ceremony artifacts and
  cached JWKS unless public verification overlap covers the applicable lifetimes. The owner must
  coordinate the scheduled four-repository rotation; this inventory neither rotates nor copies keys.

## Prerequisites, decisions and blockers before Orders 1-5

1. The owner scheduled coordinated credential-value rotation across all four repositories for the
   following morning. Key contents remain untouched. Agree the credential schema, active/retiring
   public-key overlap and signer interface first; missing required material must fail, not be
   generated or copied from another repository as an expedient.
2. Resolve the accepted one-key-per-repository design against current per-issuer global kid and
   Preference key-separation checks. Keep the cryptographic repository boundary and explicit claim
   validation. Update the owning invariant expectations only as a deliberate accepted-contract
   implementation, never a broad allowlist to hide a failure. Preference placement itself stays
   deferred; no wholesale database/ownership move is implied.
3. Define the frozen RP-to-repository JWKS mapping and key-cache behavior. Several client IDs may
   share one trusted document but still authenticate as distinct clients with independent audience,
   realm and purpose checks. Client/request input, an untrusted JWT URL header or a redirect must
   never choose the key source. Reuse existing bounded parsing only where its full policy fits.
4. The outbound-network ADR accepts direction but records owner research/concrete design as pending.
   Its allowlist format/library choice is undecided. Agree the minimum scoped design for this
   connection before adding new outbound code; do not disable TLS or public-address checking.
   VM-local/private DNS conflicts with that guard remain a future explicit decision; VM migration is
   out of this spec's implementation stage.
5. Clarify "every host of the repository" for shared JWKS. The current four Auth/Visa hosts have
   bare JWKS routes; operator tools have host-root mounts and their own guards. A broad unqualified
   route could bypass an operator guard or conflict with a mount. Specify whether every operator
   alias must expose the public JWKS and its exact route priority before changing routes.
6. Operational prerequisites are unverified: one connector per recreated Dev Container, usable
   public HTTPS/JWKS through Cloudflare Access, correctly separated host aliases and the coordinated
   credential rotation. No endpoint was contacted. Access/unlocked gate readiness and TLS trust
   cannot be inferred from local source.
7. `evidence/2026-11-09-access-tool-retirement-T8M4.md` records local rails_db/rails_performance
   removal and passed checks, but `.github/` and `.devcontainer/` are mounted read-only. Exclusive
   performance CI declarations and two Compose aliases/comment updates remain unapplied; container
   recreation and external tunnel/DNS cleanup remain owner work. These are concrete environment
   handoff items, not reasons to restore removed tools or alter unrelated operator guards.
8. `evidence/2026-11-09-access-reference-catalog-audit-N3R7.md` records 46 missing required rows in
   eleven current-model development catalogs, plus five in two retained tables, and three unresolved
   catalog definitions. No further insertion is authorized. The prior six authorization/admission/
   ceremony catalogs are complete after the approved 36-row repair, with unauthenticated Auth-entry
   redirects recorded in `evidence/2026-11-09-access-reference-repair-V4C8.md`. Full authenticated
   step-up/registration/retention workflows may still hit other missing prerequisites; do not treat
   those as remote-JWKS defects or weaken validation to get through them.
9. The authorization multiplicity/no-store work is separately recorded in
   `evidence/2026-11-09-access-authorization-multiplicity-D5K9.md` and
   `evidence/2026-11-09-access-no-store-C7P5.md`. Their recorded local tests establish the scoped
   Access refusals/cache behavior, not separated-repository sign-in. PAR, `ui_locales`/region
   derivation and the rest of AC-8 remain tracked by the accepted spec; Order 0 changes none of
   them.
